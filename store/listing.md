## Detailed description

```
For Robot Framework and Selenium: record what you do on a page and get a suite
that runs.

Recorders are not new. What they emit usually is not worth keeping: nth-child
selectors that break when someone adds a div, and Sleep 2 everywhere because
the recorder had no idea what it was waiting for. Zelector is an attempt at the
two things that actually decide whether a recorded test survives.

Built against the SeleniumLibrary documentation rather than from memory, which
shows in the details: locators use the strategy:value prefix form, the keyword
follows the element — Click Button also matches on value, Click Link on href
and link text — and Select Radio Button gets the group name and value it
actually takes rather than a locator that would fail at run time. Selenium
users working in Python or Java get the same locator scoring, and By.ID is
chosen over By.CSS_SELECTOR when the element supports it.

WAITS THAT MEAN SOMETHING

You cannot record a wait — nobody performs one — so Zelector infers it. It
watches what the page did after each action: which request fired and how long
it took, what appeared, and what appeared and then vanished. A spinner that
comes and goes is what the next step has to outlast, so that becomes
Wait Until Element Is Not Visible on it. A route change becomes
Wait Until Location Contains. Timeouts come from the time the page actually
took, not a number nobody tunes.

Every guess is shown with the reason for it, and every one is editable before
you export. Sleep is in the list, last, with a warning — hiding it only means
people type it back in by hand.

LOCATORS SCORED ON WHETHER THEY WILL LAST

Every candidate is scored, and the reason for every point lost is shown. Class
names generated by a build tool (css-1x9d8f, Button_root__3kD9a, mat-option-7)
are recognised for what they are and penalised rather than offered as if they
were stable. A selector that matches twenty elements is rejected in favour of
one that matches the element you picked. When nothing durable exists, the panel
says so while you can still go and ask for a data-testid.

THINGS THAT USUALLY GET IN THE WAY

- Closed shadow roots are walked, via a hook installed before the page's first
  script runs. DevTools shows those as an opaque dead end.
- Elements inside iframes get Select Frame and Unselect Frame around them,
  because Selenium has a current frame and a locator only ever addresses that.
- Freeze the DOM to keep a hover menu or a popover open while you inspect it.
- alert, confirm and prompt are recorded as Handle Alert and Input Text Into
  Alert. A dialog is browser chrome rather than DOM, so a recorder that misses
  one leaves a suite that hangs on it.
- Recording survives navigation, so a login or a checkout records as one flow.

ALSO COPIES A SELECTOR AS

Playwright (TypeScript and Python), Puppeteer, Cypress, plain CSS, XPath and
JSON — one element at a time, for when you are inspecting rather than
recording. Recording produces a Robot Framework suite; Playwright has codegen
built in and does its own waiting, so there is nothing here it needs.

PRIVACY

One permission: storage, for the recording in progress. No servers, no account,
no analytics, no network requests of any kind. Nothing it reads leaves your
browser. MIT licensed, and the source is public, so every word of this can be
checked against the code.

WHAT IT DOES NOT DO YET

Drag and drop, hover-only menus, keyboard-only navigation and file uploads are
not captured — those steps are simply missing from the recording rather than
recorded wrongly. Cross-origin iframes give a frame selector that is a guess,
and it is labelled as one.
```

## Single purpose

```
Generate durable element selectors and Robot Framework, Selenium and Playwright
test code from a web page, either by picking one element or by recording a flow.
```

## Permission justification — storage

```
Holds the recording in progress and the list of recently inspected elements in
chrome.storage.session. The recording must outlive the page because test flows
navigate — a login or a checkout replaces the document, which would otherwise
discard every step captured so far. Session storage is used specifically so
nothing persists after the browser closes.
```

## Permission justification — running on all sites

```
The extension patches Element.prototype.attachShadow at document_start so it can
inspect elements inside closed shadow roots, which is its main advantage over
the built-in inspector. That hook is only effective if it is installed before
the page's first script runs, so it cannot be injected on demand after the user
decides they want it. There is also no way to know in advance which site a
tester will need to work on. No data is transmitted anywhere.
```

## Remote code

Answer: **No, I am not using remote code.**

```
No remote code is used. Everything this extension runs ships inside the
uploaded package. It loads no script from any server, calls neither eval nor
new Function on fetched content, and makes no network requests of any kind.

The hooks it installs on Element.prototype.attachShadow, fetch and
XMLHttpRequest wrap functions the page already has so that closed shadow roots
can be inspected and request timings can be read. They run only code contained
in this package; they neither fetch nor execute anything from elsewhere.
```

(The last paragraph is there because a reviewer seeing `fetch` patched will
want to know whether anything is being pulled in. It is not.)

## Data collection

Nothing in any category. Google's definition of collection is transmitting data
off the user's device, and this extension makes no network requests at all. All
three certifications can be given honestly.
